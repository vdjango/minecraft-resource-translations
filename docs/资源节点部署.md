# 平台节点部署：资源下载能力

资源下载节点运行相同开源项目，不需要翻译模型密钥，也不需要主站管理员凭据。同一个平台可以提供译文缓存、资源下载或两种能力；节点按能力分别注册和配置，已有译文节点不会自动获得下载能力。

网站的开发者中心 `/developers#network` 统一展示接入和加入服务的入口；运维在同一后台的「服务节点」查看状态，在「平台设置」的下载策略、存储与同步、节点与流量、来源映射、域名与缓存页签配置资源能力。本文件说明下载工作进程的部署细节，完整平台与译文缓存部署参见 README。

## 安装与启动

要求 Python 3.11+、可访问官方上游的网络、缓存磁盘与 HTTPS 域名。

```bash
git clone https://github.com/vdjango/minecraft-resource-translations.git
cd minecraft-resource-translations
python3 -m venv .venv
.venv/bin/pip install -e .
mkdir -p /srv/buggcraft-mirror
cp deploy/resource-node.example.json /srv/buggcraft-mirror/settings.json
```

编辑 settings.json，把 `public_url` 改为自己的域名；确认磁盘配额、保留空间、类别、月出口流量与带宽预算。0 表示没有配置预算，不代表主机提供无限资源。示例是 50 GiB 资源配额、保留 10 GiB 磁盘；生产按实际主机调整。接收某类分流要求该类为 `cache`。

```bash
TRANSLATION_MIRROR_ROOT=/srv/buggcraft-mirror TRANSLATION_MIRROR_PORT=18449 .venv/bin/python -m mc_translate.mirror
```

持久运行参照 `deploy/buggcraft-mirror.service`。Windows 可用 `deploy/start-mirror.ps1 -CacheRoot <目录>`。不要两个进程共用同一缓存目录。

## 配置 HTTPS 入口

纯资源节点可以只运行资源进程。Nginx 的 HTTPS server 中代理到 loopback（证书与 server_name 按自己的域名配置）：

```nginx
location ^~ /_internal/ { return 404; }
location / {
    proxy_pass http://127.0.0.1:18449;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_buffering off;
    proxy_read_timeout 1800s;
}
```

不要公开磁盘目录或 control-token。只开放 Nginx 的 HTTPS 端口；18449 仅监听本机。如果同时部署翻译网页，使用 `deploy/nginx-mirror.conf` 和原有网页配置分路径代理。Cloudflare 规则遵循源站缓存头；307/no-store、状态接口和管理接口绕过缓存，不强制缓存跳转或错误。

### 公网端口映射与 Cloudflare Tunnel

宿迁实例的公网映射为 `17159 → 本机 443`。直连该端口可用，但 Cloudflare 的 Origin Rule 将目标端口改为 17159 后仍返回 522；源站没有收到对应连接。因此正式入口改为单独的 Cloudflare Tunnel，`mirror2.bugg.icu` 使用已代理的 CNAME 指向该隧道；只匹配此域名的旧 Origin Rule 已停用。原有 `3333`、`18443`、联机节点及 iyou 服务不变，公网 17159 保留作诊断入口。

第二台的 `buggcraft-mirror.service` 只监听 `127.0.0.1:18450`，Nginx 在本机 443 代理公开的资源路径并拒绝 `/_internal/`。专用的 `buggcraft-mirror2-tunnel.service` 将 `mirror2.bugg.icu` 转到 `https://127.0.0.1:443`，设置匹配的 Host 请求头。隧道令牌放在服务器 `/etc/buggcraft-mirror2/tunnel.token`，权限为 600，不提交仓库；因该机 UDP 7844 不通，连接使用 HTTP/2。服务、配置及 DNS 只作用于镜像域名。

该实例缓存配额为 3 GiB、磁盘保留空间为 15 GiB；主站为 5 GiB 和 20 GiB。先验证 `https://mirror2.bugg.icu/mirror-api/status` 的 `running: true`、资源 HEAD/Range 206 和 `/_internal/` 返回 404，再将其以权重 1 加到主站资源节点。若其他服务商的 Cloudflare 回源能到达高位端口，也可以用 [Origin Rules](https://developers.cloudflare.com/rules/origin-rules/) 指定端口；否则优先使用 [Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/get-started/)。直接用 IP 访问不适合作为正式 HTTPS 下载地址。

## 接入与加入

1. 请求 `https://你的域名/mirror-api/status`，确认 `protocol=buggcraft-resources-v1`、`running=true`、`enabled=true`，资源类别正确。
2. 验证已缓存资源的 HEAD、GET、Range 206、SHA-1；测试预算附近会跳转官方或备用来源。
3. 向主站管理员提交域名、名称、区域、开放资源类别与带宽。可通过仓库 issue 提交这些公开信息，不要提交管理令牌。
4. 主站在“镜像与 Cloudflare → 下载节点”填入 `https://你的域名 2` 并保存。每 20 秒检查健康，只有在线且接受下载的节点参与分流。
5. 主入口返回 307，客户端直接访问 `/_mirror_node/原始资源路径`。该路径不会再跳到其他联邦节点，资源预算不足时回退备用源或官方，避免循环。

当前为管理员明确接纳，不自动信任陌生节点。公开目录只显示健康节点的地址和权重；不会公开本地目录、预算详情、令牌。自动申请审批、客户端测速与跨节点预热是后续阶段，尚未实现。

## 外部来源映射

后台「平台设置 → 公开来源」内置多个候选仓库，并允许添加来源。映射自动扫描、核验与更新，不需要逐条导入或维护；支持原版清单匹配、Maven 公开目录扫描、文件清单 JSON 接入。每源显示已核验文件数、本地副本及下载跳转次数，可分页查看具体文件。独有资源也能通过目录或文件清单发现；无公开目录的仓库仍可匹配已知文件。国内来源优先，同地区参考服务端校验探测耗时，不能保证每个客户端的实际吞吐相同。可预览并清理匹配的本地副本，也可开启自动清理（默认关闭）；清理前重新检查外部校验、文件可达和大小，在用或共享对象受到保护。完整清单格式见 [来源发现与清理](来源发现与清理.md)。

提供商的月账单可能同时统计入站、其他应用和 CDN 回源；当前资源准入计数不等于账单。按接受的文件和 Range 长度预先计数，失败/取消/条件请求可能保守多计，进程重启后仍保留月累计。带宽按最近一分钟接受的资源字节准入，不是链路硬限速；如需精确整机带宽限制，使用系统或代理的 QoS。
